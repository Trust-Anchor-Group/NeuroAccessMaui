# Contributing

Thanks for helping improve Neuro-Access. This guide covers how work flows through the repository: branches, pull requests, the changelog, translations and issue reports. The code style itself lives in [AGENTS.md](../AGENTS.md) and applies to every change, whether a person or an AI agent writes it.

## Before you start

- Set up your machine with [Getting started](getting-started.md).
- Read [AGENTS.md](../AGENTS.md). Several of its rules differ from common .NET defaults, such as PascalCase local variables and parameters, no `var`, `this.` on every instance member and no `_` prefix on fields, so it is worth reading before your first change.
- Read the doc for the area you are about to change. The [docs index](README.md) lists them.
- If `plans/` has a folder for the feature you are touching, read it for background on decisions made earlier.

## Branches

The repository follows Git Flow.

| Branch | Purpose |
|---|---|
| `main` | Released, production-ready code. |
| `dev` | The integration branch. Finished work is merged here and tested before a release. |
| `feature/<name>` | New features. Branch from `dev` and merge back into `dev`. |
| `bugfix/<name>` or `fix/<name>` | Bug fixes found during development. Branch from `dev` and merge back into `dev`. |
| `hotfix/<name>` | Urgent fixes for a release. Branch from `main` and merge into both `main` and `dev`. |
| `release/<version>` | Release preparation. Branch from `dev`, then merge into `main`. |

Use short, descriptive branch names, such as `feature/contract-search` or `bugfix/pin-reset`.

## Making a change

1. Update your local `dev` and create a branch from it. If you work from a fork, add the main repository as `upstream` and pull its `dev` first:

   ```sh
   git remote add upstream https://github.com/Trust-Anchor-Group/NeuroAccessMaui.git
   git checkout dev
   git pull upstream dev
   git checkout -b feature/my-change
   ```

2. Make your change, following the code style and app patterns in [AGENTS.md](../AGENTS.md). Keep each pull request focused on one thing.
3. Put every new user-facing string in `AppResources.resx` and `AppResources.Designer.cs`, as described under [Translations](#translations).
4. Run the style checks and unit tests (below).
5. Push your branch and open a pull request against `dev`.

Commit messages should be short and say what changed. Add a body when the reason is not obvious from the diff.

## Checks before a pull request

Run the style and whitespace checks on the files you changed, and fix everything they report:

```sh
dotnet format style NeuroAccessMaui.sln --verify-no-changes --include path/to/First.cs path/to/Second.cs
dotnet format whitespace . --folder --verify-no-changes --include path/to/First.cs path/to/Second.cs
```

Run the unit tests:

```sh
dotnet test NeuroAccess.Nfc.Test/NeuroAccess.Nfc.Test.csproj
dotnet test IdApp.Cv.Test/IdApp.Cv.Test.csproj
```

Do not silence analyzer or style rules with `#pragma warning disable`, `[SuppressMessage]` or `.editorconfig` overrides. Fix the code instead.

Never commit secrets or the Firebase config files (`google-services.json` and `GoogleService-Info.plist`). They are git-ignored on purpose.

## Pull requests and the changelog

Every pull request uses the [pull request template](../.github/pull_request_template.md). Describe what changed and why, note anything reviewers should look at closely, and link related issues.

The template's Changelog section matters. Add one-line entries under `### Added`, `### Changed`, `### Fixed` or `### Removed`, and delete the categories you do not use, including their empty bullets. When a pull request into `dev` is merged, the [Aggregate Changelog](../.github/workflows/aggregate-changelog.yml) workflow copies those entries into the `[Unreleased]` section of [CHANGELOG.md](../CHANGELOG.md) and opens a small follow-up pull request with the update. Do not edit `CHANGELOG.md` by hand in your feature pull request.

## Translations

The app's text lives in [`NeuroAccessMaui/Resources/Languages`](../NeuroAccessMaui/Resources/Languages). `AppResources.resx` holds the English source text, and there are translations into Danish, Finnish, French, German, Norwegian, Portuguese, Romanian, Russian, Serbian, Spanish and Swedish.

To add or change text:

1. Add the key and English text to `AppResources.resx`.
2. Add the matching property to `AppResources.Designer.cs`. Visual Studio regenerates this file when you edit the `.resx` in its designer. Other editors do not, so add the property by hand, following the existing ones.
3. Use the key from C# with `ServiceRef.Localizer[nameof(AppResources.MyKey)]` and from XAML with `{l:Localize MyKey}`.

The other languages are generated by [`Translation/TranslateResources.bat`](../Translation/TranslateResources.bat), so you normally do not translate by hand. The script runs on Windows from the `Translation` folder and uses the translation utility from a built [IoT Gateway](https://github.com/PeterWaher/IoTGateway) checkout placed next to this repository.

## Reporting issues

Report bugs and suggest features in [GitHub Issues](https://github.com/Trust-Anchor-Group/NeuroAccessMaui/issues). Search first to see if someone already reported it. A good report includes:

- Steps to reproduce the problem.
- What you expected and what happened instead.
- Screenshots or error messages, if you have them.
- The platform, OS version and app version.

Do not report security problems in a public issue. Contact Trust Anchor Group through [trustanchorgroup.com](https://trustanchorgroup.com/) instead.

## AI coding agents
